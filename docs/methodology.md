# 방법론 및 한계

## 1. 이 DB가 하는 일과 하지 않는 일

**하는 일** — 4개 규제 체계의 항공기 충돌 관련 요건을 동일한 15개 비교 축
(`corpus/crosswalk/topics.yaml`)으로 정규화하고, NEI 07-13을 기준선으로 각 문서의
상대적 위치를 명시하며, 이를 BM25 검색과 LLM 인용이 가능한 형태로 제공합니다.
15개 소스 중 14개는 원문이 축자 색인되어 있어 조문 단위 인용이 가능합니다.

**하지 않는 일** — 규제 준수 판단, 설계 적합성 판정, EUR 요건 본문 제공.

## 2. 출처 검증 정책

이 DB의 설계 원칙은 **"모르는 것을 아는 것처럼 저장하지 않는다"** 입니다.

모든 조항 레코드는 두 축으로 표시됩니다.

- `text_status`: `verbatim`(원문 인용) / `summary`(요약) / `editorial`(편집자 주)
- `verification`: `primary_source` / `web_verified` / `model_knowledge` / `to_verify`

검색 결과에 `★ ✓ ~ !` 기호로 노출되고, `scripts/answer.py`의 시스템 프롬프트가
모델에게 이 등급을 답변에 반영하도록 강제합니다.

현재: `primary_source` 50 · `web_verified` 1 · `model_knowledge` 0 · `to_verify` 0.
남은 `web_verified` 1건(NRC AIA 검사 프로그램)은 코퍼스 문서가 아니라 웹페이지가 출처이므로
승격 대상이 아닙니다.

## 3. 원문 확보 경로

이 DB의 실행환경은 아웃바운드 HTTPS가 조직 egress 정책으로 **전면 차단**되어
있습니다. `ecfr.gov`, `nrc.gov`, `sujb.gov.cz`, `zakonyprolidi.cz`,
`www-pub.iaea.org`, `eur-lex.europa.eu`, `wenra.eu`, `govinfo.gov`가 모두 CONNECT
단계에서 403을 반환하며, 허용된 호스트는 패키지 레지스트리와 Anthropic API뿐입니다.
정책 거부이므로 TLS 검증 해제나 프록시 우회로 회피하지 않았습니다.

원문은 전부 **사용자가 제공**했습니다 — Google Drive 커넥터와 직접 업로드.
Drive의 `download_file_content` 경로가 중간에 고장났을 때는 `read_file_content`로
텍스트를 추출해 우회했습니다. 스캔본(텍스트 레이어 없음)은 이 환경에 OCR 엔진이
없어 읽지 못했고, 사용자가 텍스트본으로 다시 제공했습니다.

## 4. 원문 대조로 정정된 사항

요약본으로 먼저 구축한 뒤 원문을 확보하는 순서였기 때문에, 원문 대조 단계에서
여러 오류가 드러났습니다. 모두 해당 레코드에 정정 이력을 남겼습니다.

| 항목 | 초기 기재 | 원문 확인 결과 |
|---|---|---|
| 10 CFR 50.150(d) | 평가결과 비공개 조항 | **일몰 조항** — 2027.4.8. 실효 |
| 비공개 근거 | 50.150(d) + 2.390 | RG 1.217 Section A의 **SGI 통제** |
| RG 1.217 승인 | 단서 없어 보임 | Position 2 — **참조문서는 미승인** |
| 체코 항공기 조항 | § 13(2)(b) | **§ 11(4)(b)** |
| 체코 일반 외부사건 | § 6, § 12 | **§ 11(1)~(3)** |
| 체코 고의충돌 | 설계 시행령 밖 | **§ 10(1)(d)** — 시행령 안 |
| 1E-7 출처 | SSG-79 → (오정정) SSG-68 | **양쪽 모두** 수록, SSG-79가 NS-G-3.1 대체 |
| EUR 우발 설계기준 | 복수 위협 시나리오 | **경항공기 + 군용기** (대형기 아님) |
| SRS-88 여유도 | HCLPF 개념 | **계층적 접근**, HCLPF는 선택지 중 하나 |

특히 마지막에서 세 번째 항목은 제 **정정 자체가 틀렸던** 경우입니다. 초기 기재가
맞았고, 중간 단계의 "정정"이 과했습니다. 그런 경우도 되돌린 이력을 남겼습니다.

## 5. 남은 한계

- **EUR 요건 본문 없음.** 공개 챕터 목차로 구조(조·항 번호와 제목)는 확정했으나
  Figure 4·5·6의 하중값, 성능목표 수치, 하중조합, 저항수준 정의는 라이선스 대상입니다.
- **위협 파라미터의 3자 수치 비교는 원리적으로 불가능**합니다. 미국은 SGI 통제,
  EUR은 라이선스. 이는 자료 부족이 아니라 각 체계의 정보통제 정책의 결과입니다.
- **세 체계가 서로 다른 사건을 다룹니다**(CW-03). 미국은 대형 상용기, EUR 우발은
  경항공기·군용기, 체코는 1E-7/년 초과 모든 낙하물체. 어떤 비교든 이 전제를
  먼저 밝혀야 합니다.
- 모든 조항 레코드가 원문 대조를 마쳤습니다(`model_knowledge` 0, `to_verify` 0).

## 6. 청킹 전략

- **큐레이션 레코드**: 조항 1건 = 청크 1개. 조항이 이미 의미 단위이고 분할하면
  인용 단위가 깨집니다. 영문·국문 요약을 한 청크에 함께 넣어 두 언어 질의가 같은
  레코드에 도달하게 했습니다.
- **원문 청크**: 문단 단위로 묶어 약 1200자, 겹침 150자. `§`, `3.47`, `2.4.1` 형태의
  조문 표기를 정규식으로 추출해 locator로 붙입니다.
- 모든 청크가 자체 인용 헤더를 포함해, 하나만 떼어 프롬프트에 붙여도 출처를
  잃지 않습니다.

## 7. 검색 동작

FTS5 `unicode61 remove_diacritics 2` 토크나이저를 사용합니다. 체코어 분음부호를
정규화하고, 한글은 공백 단위로 정상 토큰화됩니다. 질의어가 조사와 붙어 색인어와
어긋나는 경우를 대비해 LIKE 기반 부분문자열 폴백을 둡니다.

`retrieval.expand_with_crosswalk()`는 검색된 조항을 인용하는 크로스워크 항목을
자동 추가합니다. "미국과 체코 차이"류 질의는 크로스워크가 답을 갖고 있는데 한쪽
문서의 용어로 질의하면 그 조항만 검색되기 때문입니다.

## 8. 무결성 검사

`crosswalk.clause_ids`는 JSON 배열이라 SQLite가 외래키로 강제하지 못합니다.
레코드를 자주 교체하는 코퍼스라 끊어진 참조가 생기면 인용이 조용히 누락되므로,
`build_db.py`가 끊어진 참조를 발견하면 빌드를 실패시킵니다. 마찬가지로
`make_matrix.py`는 크로스워크에 입장이 있는데 매트릭스 열이 없는 소스를 발견하면
실패합니다 — 비교 결과가 표에서 조용히 사라지는 것을 막기 위함입니다.

## 9. 벡터 검색 추가

`chunks.embedding`(BLOB), `chunks.embedding_model`(TEXT) 컬럼이 비어 있습니다.
임베딩을 채우거나 `scripts/export_rag.py`로 JSONL을 내보내 외부 벡터 스토어에
적재하십시오. 현재 2,262청크 규모에서는 BM25만으로도 재현율이 충분하나,
의미 기반 질의가 많아지면 하이브리드 검색이 유의미합니다.
