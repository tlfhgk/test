# 방법론 및 한계

## 1. 이 DB가 하는 일과 하지 않는 일

**하는 일** — 4개 규제 체계의 항공기 충돌 관련 요건을 동일한 15개 비교 축
(`corpus/crosswalk/topics.yaml`)으로 정규화하고, NEI 07-13을 기준선으로 각
문서의 상대적 위치를 명시하며, 이를 BM25 검색과 LLM 인용이 가능한 형태로
제공합니다.

**하지 않는 일** — 규제 준수 판단, 설계 적합성 판정, 인허가 문서에 그대로 인용
가능한 축자 인용문 제공. 마지막 항목은 `scripts/ingest_raw.py`로 원문을
색인하면 해결됩니다.

## 2. 출처 검증 정책

이 DB의 설계 원칙은 **"모르는 것을 아는 것처럼 저장하지 않는다"** 입니다.

모든 조항 레코드는 `text_status`와 `verification` 두 축으로 표시됩니다.

- `text_status`: `verbatim`(원문) / `summary`(요약) / `editorial`(편집자 주)
- `verification`: `primary_source` / `web_verified` / `model_knowledge` / `to_verify`

`editorial` 레코드(예: `CZ-malicious-separation`)는 인용문이 아니라 구조적
해석입니다. "고의충돌은 체코에서 어디에 규정되어 있는가"라는 검색에 대해
"이 DB에는 답이 없고, 답은 물리적방호 규정에 있을 것"이라는 사실 자체를
반환하기 위해 존재합니다. 침묵보다 명시적 부재 표시가 낫다는 판단입니다.

## 3. 구축 시 제약 (중요)

이 DB는 아웃바운드 HTTPS가 조직 egress 정책으로 제한된 환경에서 구축되었습니다.
`ecfr.gov`, `nrc.gov`, `law.cornell.edu`, `sujb.gov.cz`, `zakonyprolidi.cz`,
`tzb-info.cz`, `www-pub.iaea.org` 등 **모든 원문 도메인이 403으로 차단**되어
원문 PDF·HTML을 직접 확보하지 못했습니다.

따라서 현재 코퍼스는 다음 두 경로로만 작성되었습니다.

1. 웹 검색 결과로 확인된 내용 → `verification: web_verified`
2. 확인하지 못한 배경지식 → `verification: model_knowledge` 또는 `to_verify`

**축자 인용문은 단 한 건도 수록하지 않았습니다.** 확인할 수 없는 원문을
그럴듯하게 재구성하는 것이 이 용도에서는 가장 위험한 실패 모드이기 때문입니다.
조문번호가 불확실한 경우 locator에 `(§ to_verify)`를 남겼습니다.

## 4. 알려진 공백

`python3 scripts/report_gaps.py`가 항상 최신 목록을 출력합니다. 구축 시점의
주요 공백은 다음과 같습니다.

| 레코드 | 공백 내용 | 해소 방법 |
|---|---|---|
| `US-RG-1.217-exceptions` | RG 1.217이 NEI 07-13 Rev.8 승인에 붙인 명확화·예외사항 미확인 | ADAMS ML092900004 확보 후 재색인 |
| `CZ-329-2017-external-events-general` | 시행령 조문번호(§) 미확인 | SÚJB 공식 PDF 확보 |
| `CZ-378-2016-siting` | 부지 시행령 번호 자체가 미확인 | 체코 관보 확인 |
| `US-10CFR50.150-a-3`, `-b`, `-c`, `-d` | 항·호 세부 구조 미확인 | eCFR 대조 |
| `CW-08` | NEI 07-13과 IAEA SRS 87이 각각 채택한 관통·박리 경험식(수정 NDRC, Degen, Chang 등)의 일치 여부 | 양 문서 원문 색인 후 비교 |

CW-08은 이 비교의 가장 실질적인 미해결 기술 질문입니다. 두 문서 모두 국부손상
평가식을 제공한다는 사실까지는 확인되나, 어떤 경험식을 채택했고 결과가 일치하는지는
요약 수준에서 답할 수 없습니다.

## 5. 청킹 전략

- **큐레이션 레코드**: 조항 1건 = 청크 1개. 조항 자체가 이미 의미 단위이고
  분할하면 인용 단위가 깨지기 때문입니다. 영문·국문 요약을 한 청크에 함께 넣어
  두 언어 질의가 같은 레코드에 도달하게 했습니다.
- **원문 청크**: 문단 단위로 묶어 약 1200자, 겹침 150자. 규정 두어 문단 정도가
  인용 검증이 가능한 최소 단위입니다. `§`, `3.47`, `2.4.1` 형태의 조문 표기를
  정규식으로 추출해 locator로 붙입니다.
- 모든 청크는 자체 인용 헤더를 포함합니다. 검색 후 청크 하나만 프롬프트에
  붙여도 출처를 잃지 않게 하기 위함입니다.

## 6. 검색 동작

FTS5 `unicode61 remove_diacritics 2` 토크나이저를 사용합니다. 체코어 분음부호
(`vyhláška`, `jaderného`)를 정규화하고, 한글은 유니코드상 문자로 분류되므로
공백 단위로 정상 토큰화됩니다. 질의어가 조사와 붙어 색인어와 어긋나는 경우
(`항공기충돌` vs `항공기 충돌`)를 대비해 LIKE 기반 부분문자열 폴백을 둡니다.

`retrieval.expand_with_crosswalk()`는 검색된 조항을 인용하는 크로스워크 항목을
자동으로 추가합니다. "미국과 체코 차이"류 질의는 크로스워크 레코드가 답을
갖고 있는데, 한쪽 문서의 용어로 질의하면 그 조항만 검색되기 때문입니다.

## 7. 벡터 검색 추가

`chunks.embedding`(BLOB), `chunks.embedding_model`(TEXT) 컬럼이 비어 있습니다.
임베딩을 채우거나, `scripts/export_rag.py`로 JSONL을 내보내 외부 벡터 스토어에
적재하십시오. 현재 코퍼스는 57청크 규모로 BM25만으로도 재현율이 충분하며,
원문을 색인해 수천 청크가 되면 하이브리드 검색이 유의미해집니다.
